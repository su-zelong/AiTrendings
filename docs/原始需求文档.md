# AiTreadings v2.0 需求文档（当前迭代）

## 1. 本期目标
在现有“抓取 Trending → LLM 总结 → 推送”流水线基础上，**升级分析质量**，让每个项目输出更具决策价值的信息，并支持同类别项目横向对比。

**不涉及**：用户订阅、交互式查询、管理控制台、历史趋势图谱。

---

## 2. 核心功能需求

### 2.1 开发者采纳指数（Adoption Score）
- 对每个分析的项目计算一个 0~100 的评分，综合以下因子：
  - **基础因子**：stars、forks、open_issues 数量、contributors 数。
  - **动态因子（必须）**：
    - **热力加速度**：`(今日stars - 昨日stars) / 昨日stars`，需连续记录至少 3 天数据。
    - **活跃度衰减**：若 `last_push_date` 距今 > 90 天，总得分 × 0.7。
- 输出字段：`adoption_score`（总分）及 `score_breakdown`（各分项得分）。

### 2.2 横向对比（按类别）
- **前提**：LLM 分析 README 时，必须额外输出一个 `category` 字段（如 `Web Framework`, `Database`, `CLI Tool`），用于归类。
- **对比逻辑**：
  - 在每日报告中，取 **近 7 天内** 所有上榜项目，按 `category` 分组。
  - 每组内按 `adoption_score` 或 `stars 增速` 排序，生成对比表格（含项目名、stars增速、采纳指数、简要说明）。
- 输出位置：Markdown / HTML 报告中的新增板块。

### 2.3 风险提示
- 输出字段：`risk_level`（低/中/高）及 `risk_reason`（简要说明）。
- 风险判定依据：
  - 许可证未明确（`license` 为空或 non-standard）。
  - 近 6 个月无正式 release。
  - open_issues 数 > stars 数的 10% 视为“维护压力大”。

---

## 3. 数据存储与支撑

### 3.1 存储选型（甲方拍板）
- **PostgreSQL 15+**（若团队运维能力有限，可用 SQLite 过渡，但 SQL 必须兼容 PG）。
- **不使用图数据库**：本期及可预见的将来，数据关系简单，PG 的窗口函数和 JSONB 足以满足横向对比需求。

### 3.2 数据表设计（只需两张表）

#### 表1：`trending_snapshots`（每日快照）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | SERIAL | PK |
| project_name | VARCHAR(255) | 唯一标识（owner/repo） |
| category | VARCHAR(50) | LLM 提取的分类（来自最新分析） |
| stars | INT | 当日总 stars |
| forks | INT | 当日总 forks |
| delta_stars | INT | 相比上一日快照的增量（需计算） |
| snapshot_date | DATE | 快照日期 |
| raw_metadata | JSONB | 其他字段（license, last_push, contributors, open_issues） |

**索引**：`(category, snapshot_date DESC)` 联合索引。

#### 表2：`analysis_cache`（LLM 结果缓存）
| 字段 | 类型 | 说明 |
|------|------|------|
| readme_md5 | CHAR(32) | PK |
| llm_response | JSONB | 完整 LLM 输出（含 adoption_score, category, risk_level 等） |
| created_at | TIMESTAMP | |
| expires_at | TIMESTAMP | 默认 30 天后过期 |

---

## 4. 性能与成本控制约束

- **缓存强制**：每次分析前，计算 README 内容的 MD5，若缓存存在且未过期，直接复用，**严禁重复调用 LLM**。
- **并发**：爬取 Top N 项目时，使用 Go 协程并发抓取 GitHub API 和调用 LLM，单次全流程耗时不得超过 **2 分钟**。
- **数据清理**：自动删除 `trending_snapshots` 中超过 30 天的快照（除非项目连续上榜，但本期可不做复杂处理）。

---

## 5. 验收标准（本期交付检查点）

- [ ] LLM 输出 JSON 中新增字段：`category`, `adoption_score`, `score_breakdown`, `risk_level`, `risk_reason`。
- [ ] 生成的报告（Markdown/HTML）中包含按 `category` 分组的横向对比表格（含近 7 天项目）。
- [ ] 数据库正确存储每日快照，且 `delta_stars` 通过前一日数据计算得到。
- [ ] 缓存生效：相同 README 再次抓取时，日志显示“cache hit”，无 LLM 调用。
- [ ] 单元测试覆盖核心计算逻辑（采纳指数、风险判定）≥ 80%。

---

## 6. 本期不包含（明确排除）
- ❌ 个性化订阅与多用户分发
- ❌ 交互式查询（`-query` 或消息回调）
- ❌ Web 管理控制台
- ❌ 历史趋势图和长期学习图谱
